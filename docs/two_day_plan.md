# Two-day execution plan — USDRUBF Nowcasting

**Подготовлен:** 2026-11-20 · **Период:** следующие два рабочих дня · **Команда:** A/B/C/D  
**Ограничения:** только daily OHLCV из текущего MOEX ISS; `conditional EOD / pseudo-PIT`; final test 2026 закрыт.

## Результат двух дней

1. Воспроизводимый baseline RW/AR из чистого `main` с актуальным manifest и без открытия final test.
2. PIT-каталог внешних данных и первый документированный feature panel (пусть небольшой).
3. Один простой внешне-факторный benchmark (Ridge/регрессия) и опциональная PCA, если позволяет панель.
4. Интервальный benchmark RW (90%/95%) на h=1…7 и оценка coverage/width/interval score.
5. Общий `docs/project_status.md` + реестр экспериментов с версиями кода/данных и ограничениями.

## День 1 — подготовка интерфейсов и данных

| Кто | Приоритет | Действия | Артефакт / DoD |
|---|---|---|---|
| **A — Research Lead** | P0 | Новый чистый checkout `main`; `pytest`, `python -m benchmarks.run`, `python -m benchmarks.compare`; сверить 254 общие validation пары на каждый h, RMSE и закрытие final test | Новый run directory с manifest, Git SHA, `git_status=clean` или объяснением; `comparison.passed=true`; обновлённый research log |
| **B — Data Engineer** | P0 | Документировать точно `CANDLE_CLOSE` и режим появления дневной свечи; подтвердить/маркировать предположения календаря; собрать курс ЦБ, историю funding (если доступна) и 2–3 внешних ряда; каждому полю указать источник, дату наблюдения, `published_at/available_at` или консервативный лаг | `data_dictionary`, raw-файлы и первоначальная `features_daily` с прозрачными статусами доступности; ни одного неизвестного timestamp, выданного за фактический |
| **C — Quant Modeling** | P1 | Составить узкую модель факторов (валютные, ликвидность, внешний риск); реализовать Ridge на `Δ_h CLOSE` как альтернативный baseline с train-only fit и совместимым `generate_forecasts` API | Код Ridge, тесты, краткая model spec; пока без заявления OOS-преимущества |
| **D — Uncertainty** | P1 | Реализовать coverage, mean width, interval score, RW-интервалы по историческим h-дневным изменениям; соблюдать задержку доступности h-шаговых меток | Интервальный API + тесты no-leakage, предварительная validation-таблица 90%/95% |

**Синхронизация:** A и B согласуют одно значение `origin_date`/доступности; A выдаёт C и D контракт интерфейса и immutable validation origin/target keys. Не ждать большой факторной панели для реализации интервалов RW.

## Порядок работы и review

- **Контрольная точка 1:** B показывает источник/политику лагов, A подтверждает разрешённость признаков; C не начинает итоговую оценку с небезопасной панелью.
- **Контрольная точка 2:** A подтверждает повторяемость RW/AR и стабильные validation keys; D может работать параллельно.
- **Контрольная точка 3:** C/D передают прогнозы без фактических будущих значений; A оценивает в одном scoring pipeline.
- **Контрольная точка 4:** на вечернем review команда фиксирует `implemented` vs `validation-supported` vs `untested`, сохраняет неудачные гипотезы.

## Definition of Done (два дня)

- [ ] Base RW/AR reproduction из чистого коммита + зафиксированная версия run.
- [ ] Feature dictionary с provenance, `available_at` или явно указанной lag assumption.
- [ ] Внешне-факторный Ridge с честными validation-прогнозами **либо** документированная причина data-blocked.
- [ ] RW-интервалы, метрики coverage/width/score на h=1…7.
- [ ] Чётко зафиксирована доступность исторического CLOSE/calendar: verified или conditional/pseudo-PIT.
- [ ] Ни один результат final test не использован в настройке.
- [ ] Updated project status, hypothesis/decision log и краткий список go/no-go условий DFM.

## Важные методологические оговорки

- `h=1,…,7` — торговые даты **по предоставленному календарю**. Его независимость ещё не подтверждена целиком.
- Любые `HIGH/LOW/CLOSE` за d появляются в информационном множестве только после готовности свечи d.
- Для h-дневного supervised target `C_{t+h}-C_t` строка может войти в fit лишь после доступности `C_{t+h}`; не достаточно одного только `feature_date <= origin`.
- При асинхронных публикациях не заполнять позднее публикуемый фактор по календарной дате без as-of.
- На этапе разработки не заявлять `TEST_CONFIRMED` ни для одной модели или новой гипотезы.
