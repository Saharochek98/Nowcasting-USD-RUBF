# Backtesting Protocol — USDRUBF

**Версия:** 1.0 · 2026-11-19 · Владелец: Research Lead & Backtesting (A)  
**Статус:** проект протокола; календарь и timestamp — `OPEN` до проверки источника

## 1. Объект прогноза

- Инструмент: USDRUBF, рыночная цена последней доступной сделки на ежедневном фиксированном срезе.
- Предлагаемый базовый горизонт: `h=1,…,7` **торговых дней**. Требуется сверить с требованием «7 дней» из исходной постановки и согласовать переход к календарным дням при необходимости.
- Каждое наблюдение имеет `forecast_origin` (полная временная метка в выбранной зоне), `target_timestamp`, `horizon`, `target_price` и отметку доступности.
- В случае отсутствия сделки в момент среза используем заранее определённое правило последней допустимой сделки с предельным возрастом котировки; **не** переносим цену без ограничений.
- ЦБ/USD-RUB, фандинг, расчётная цена — потенциальные признаки, **не** таргет; их временная доступность проверяется.

## 2. Информационное множество

Для любого входного значения `x`: `available_at(x) <= forecast_origin`. Для пересматриваемых данных учитываем публикационный винтаж. Если архив винтажей отсутствует, записываем режим `pseudo-PIT` и ограничение в отчёте.

Принцип: «дата, за которую сообщено значение» не равна «моменту, когда значение было известно». Данные клиринга/фандинга, опубликованные после среза, исключаются.

## 3. Формирование данных и фичей

- Хранить исходные сырые записи и UTC/локальную временную метку, исходную зону и время публикации.
- Формировать признаки разностей/лог-доходностей только для корректных положительных рыночных цен; пропуски и выбросы документировать, не исправлять исходную цену произвольно.
- `fit` стандартизаторов, PCA, селекторов, импутеров — только на обучающем окне каждой итерации.
- Любые исторические признаки ошибки прогноза доступны только после фактической публикации целевого значения; для `h=7` это особенно важно.

## 4. Разбиение и walk-forward

1. Выделить хронологические `train`, `validation`, `final test` после аудита длины ряда. Точные даты **не задавать до проверки фактической доступности**.
2. Подбор признаков, числа факторов, гиперпараметров, параметров усадки и калибровки — **только** в train/validation; final test остаётся нетронутым.
3. В каждом origin `τ_t` обучать модель только на парах, метки которых были известны к `τ_t`; прогнозы horizon `h` сохранять до появления целевого значения.
4. Переобучение (expanding/rolling) и частоту обновления определить заранее в конфигурации; одинаковые origin и target timestamps для сравниваемых моделей.
5. Для ML-коррекции использовать **исторические OOS-предсказания** базовой модели, доступные на время построения новой коррекции; не использовать in-sample residuals как будто они OOS.
6. Учесть перекрытие прогнозных горизонтов при доверительных интервалах на разность ошибок (например, block bootstrap или HAC, когда уместно).

## 5. Benchmark и матрица сравнения

- B0 Random Walk: `F_hat(t+h|t)=F_t`.
- B1 RW with drift: `F_hat=F_t+h*mu_hat_t`, где `mu_hat_t` — среднее изменение на доступной обучающей истории для выбранной торговой шкалы.
- B2 Спред к последнему доступному курсу ЦБ: `b_t=F_t-S_CBR_latest_asof(t)`; обучить простую регуляризованную регрессию будущего изменения цены от лагов `b_t`, оценивать как гипотезу.
- M1 PCA + регрессия, M2 DFM/Kalman, M3 DFM+ML, M4 интервальная коррекция/усадка.

## 6. Метрики

Для `e_{t,h}=F_{t+h}-F_hat_{t+h|t}`:

- `MAE_h=mean(|e|)`
- `RMSE_h=sqrt(mean(e^2))`
- `Bias_h=mean(e)`
- `RMSE_ratio_h = RMSE_model,h / RMSE_RW,h` на **общем наборе дат**; меньше 1 означает меньший RMSE на этом наборе, но не автоматическую статистическую значимость.
- Для интервалов `PICP_h` (доля попаданий), `MPIW_h` (средняя ширина), interval score для номинального покрытия `1-alpha`.
- Как минимум уровни интервалов `90%` и (если достаточно данных) `95%`; окончательные уровни фиксируются до оценки.

Публиковать результаты для каждого горизонта и число оценённых прогнозов; итоги по горизонтам не подменяют покомпонентные результаты.

## 7. Анти-leakage тесты

- Предиктор с `available_at > forecast_origin` должен отбрасываться/вызывать ошибку.
- В training не включается строка, чья target-публикация позднее момента обучения.
- Скейлер/импутер/PCA обучены только на train-fold.
- Перемешивание дат запрещено.
- Test не участвует в выборе модели.
- Сопоставление по `(forecast_origin, target_timestamp, horizon)` строго уникально; обнаруженные пропуски не дозаполнять будущими данными.
- Проверка доступности курса ЦБ и расчётных показателей в сценариях до/после их публикации.

## 8. Контракт вывода предсказаний

Обязательные столбцы: `model_id, model_version, forecast_origin, target_timestamp, horizon, prediction, train_end_timestamp, data_version`. Для интервалов дополнительные: `alpha, lower, upper, calibration_end_timestamp`.

Сохранить CSV/parquet прогнозов, YAML/JSON конфигурацию, git commit hash, сведения о данных и результаты метрик. Эксперименты не переписывать задним числом.

## 9. Протокол принятия решения

Любое улучшение, обнаруженное на validation, требует проверки на отдельном final test. Если PIT не подтверждён, результат маркируется `pseudo-PIT`. Если календарь/таргет не согласованы — остановить запуск финального бэктеста.
