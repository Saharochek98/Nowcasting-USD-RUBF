# Backtesting Protocol — USDRUBF

**Версия:** 1.3 · **Дата:** 2026-11-20 · **Владелец:** A  
**Статус:** RW/AR(1) validation реализован и сохранён; источник `MOEX ISS CANDLE_CLOSE` документирован, время доступности свечи всё ещё не подтверждено (conditional EOD / pseudo-PIT).

## 1. Определение target и origin

- `instrument=USDRUBF`; данные **дневные OHLC**, торговый календарь фактический, при необходимости локальная зона биржи `Europe/Moscow`.
- `target_price[d]=CLOSE_d` исходного источника, **условно** при подтверждении, что CLOSE — рыночная дневная цена. Не предполагать его тождество последней сделке в 23:50 или расчетной цене клиринга.
- `forecast_origin[d]` — момент **после завершения и доступности дневной OHLC-свечи за d**. Точный timestamp пока `UNKNOWN`; 23:51 МСК не утвержден.
- `h=1,…,7` — следующие **торговые дни USDRUBF** (не автоматически календарные и не сдвиги по непустым строкам).
- Если фактические `available_at` отсутствуют, применять и явно маркировать допущение **conditional EOD / pseudo-PIT**. Нельзя утверждать достоверный прогноз в конкретную минуту.
- Факт существования дневной строки не доказывает, что ее OHLC были доступны в этот же момент. Для `HIGH/LOW/CLOSE` дня `d` допускается использование только **после готовности всей свечи**.

## 2. Фандинг, официальный курс, клиринг

- Использовать только **опубликованный** к origin фандинг и последний **опубликованный** курс ЦБ; для каждого значения хранить `observation_time`, `published_at`, `available_at`, `vintage`, `rule_version`.
- По спецификации USDRUBF от 08.09.2026: расчетная цена для вариационной маржи — последний опубликованный курс ЦБ (п. 2.1.7); `SwapRate` связан с VWAP торгов 10:00–15:30 и курсом ЦБ, установленным в этот торговый день (п. 2.1.3).
- Не использовать итоги клиринга, фандинг или курс ЦБ, если они появились **после фактического forecast_origin**; когда timestamp публикации отсутствует, отметить допущение о лаге и использовать консервативный лаг либо исключить такой признак. Даты действия курса не смешивать с датами публикации.
- Исторические изменения параметров фандинга и режимов торгов проверять с `effective_from`, а не применять актуальные правила ретроспективно.

## 3. Дневные OHLC, пропуски и контроль качества

Ожидаемые данные от B: `trade_date, OPEN, HIGH, LOW, CLOSE`, опционально `VOLUME`, а также `price_type, source, available_at (if known), data_version`. Отдельно — **независимый торговый календарь USDRUBF**, включающий торговые дни без записей котировок.

Обязательный первичный аудит:
1. Даты, дубликаты, сортировка, глубина истории, торговый календарь, необычные пропуски и приостановки.
2. Отсутствующие, нечисловые и неположительные OHLC; целостность `HIGH >= max(OPEN,CLOSE)`, `LOW <= min(OPEN,CLOSE)`, `HIGH >= LOW`.
3. Подозрительные дневные изменения и потенциальные ошибки выгрузки — изучить, но не удалять автоматически только из-за размера движения.
4. Проверить, что поле `CLOSE` — рыночное закрытие, **а не settlement/clearing**; если семантика не подтверждена, остановить основной модельный эксперимент.
5. Подсчитать число доступных origin/target пар для каждого горизонта `h=1,…,7`.

**Обработка отсутствующих свечей:** не заполнять target вперед, курсом ЦБ, нулями или клиринговой ценой. Сохранять торговый день в календаре. При отсутствии `CLOSE_d` пропустить origin для моделей с известным последним CLOSE; при отсутствии `CLOSE_{d+h}` записать `unscored`, не изменяя h. AR-модель обучать на разностях **соседних торговых дней с обеими валидными ценами**, не считать разницу через пропуск однодневной.

Исторические внутридневные сделки, bid/ask, возраст котировок, VWAP и пороги 5/15/30 минут **не проверяются**: соответствующих данных у команды нет.

## 4. Point-in-time и walk-forward

Для каждого `x` требуется `available_at(x) <= forecast_origin[d]`, включая дневной CLOSE, курс ЦБ, фандинг, макроряды и историю ошибок. Когда фактический timestamp/винтаж недоступен, фиксировать консервативное предположение о лаге и маркировать `conditional EOD / pseudo-PIT`; не маскировать его под подтвержденную доступность.

- Сначала выбрать train/validation/final test по хронологии после аудита длины истории; test не открывать для model selection.
- На каждом origin модель видит только исторические обучающие пары, у которых **метка уже стала доступна** к этому origin.
- Масштабирование, PCA, отбор признаков, импутацию и гиперпараметры оценивать только на разрешенных окнах.
- Для ML-коррекции использовать историю **реальных OOS-прогнозов** DFM, у которых target уже известен на дату новой коррекции. `h=7` имеет задержку как минимум семь торговых шагов.
- Отдельно фиксировать пересекающиеся прогнозы горизонтов и учитывать зависимость ошибок (HAC/block bootstrap при уместности).

## 5. Benchmarks

B0 RW: `C_hat[d+h|d]=C_d`. **B1 AR(1) на дневных разностях CLOSE**: `ΔC_d=c+φΔC_{d-1}+ε_d`, OLS на известной истории, рекурсивная сумма прогнозных разностей на 1–7 торговых шагов. B2 drift (дополнительно): `C_d+h*mu_hat_d`. B3 spread/funding regression (при подтвержденных PIT-данных). Далее PCA, DFM, DFM+ML, интервальная коррекция.

## 6. Метрики и честность сравнения

Точечные: `MAE_h`, `RMSE_h`, `Bias_h`, `RMSE_ratio_h=RMSE_model_h/RMSE_RW_h`; считать **на общих origin/target**; `n_h` и даты сообщать. Интервалы: empirical coverage, mean width, interval score, отдельно по `h` и уровню (первый вариант 90% и 95%).

Нельзя объявлять значимость только на основании `RMSE_ratio<1`. Показывать анализ по режимам и чувствительность к пропущенным дням.

## 7. Обязательные автоматические тесты

1. Дубликаты дат запрещены; дата принадлежит календарю USDRUBF, торговые дни без свечей сохраняются.
2. OHLC числовые/положительные, `HIGH >= max(OPEN,CLOSE)`, `LOW <= min(OPEN,CLOSE)`.
3. При отсутствии `CLOSE` нельзя получить искусственное нулевое изменение или новый таргет от forward-fill.
4. `target_date(d,h)` — h-й следующий торговый день по независимому календарю, **не** h-я следующая непустая дата.
5. RW использует `C_d`, AR параметры обучаются только на доступных прошлых **полных** изменениях.
6. Входные OHLC дня d считаются доступными только после завершения свечи; признаков с подтвержденным `available_at > forecast_origin` быть не должно.
7. Ни одна обучающая h-шаговая метка с публикацией позже origin не допускается; fit-transform только на train.
8. Все модели сравниваются по одинаковым `(forecast_origin, target_date, horizon)`, финальный test не участвует в настройке.

## 8. Файлы и контракт прогнозов

Прогнозы: `model_id, model_version, forecast_origin, origin_date, target_date, horizon, prediction, train_end_date, data_version, source, pit_status`.
Оценка отдельно после возникновения факта: `actual, scored_status, error`. Дополнительно интервал: `alpha, lower, upper, calibration_end_date`.

Сохранять raw OHLC, определения поля CLOSE, торговый календарь, отчет качества, конфигурации, версию Git и все предсказания (включая `unscored`). Если timestamp неизвестен, хранить `forecast_origin_mode=conditional_EOD` вместо выдуманного времени.

## 9. Текущее состояние реализации и воспроизводимости (20.11.2026)

- Текущий runnable pipeline: `benchmarks/core.py`, `benchmarks/run.py`, `benchmarks/calendar.py`, `benchmarks/compare.py`; tests — `tests/`.
- Канонические предварительные validation-артефакты: `results/benchmark_calendar_v2/`; исторический `results/benchmark_run/` хранится для проверки воспроизведения A1→A2, **не** заменяет v2.
- Train / validation / final test (по **дате target**, включительно): 2022-04-26—2024-12-31 / 2025-01-01—2025-12-31 / 2026-01-01—2026-11-18. Наблюдений соответственно 683 / 254 / 223. На validation каждая из 7 метрик сформирована по 254 общим scored парам.
- B1: expanding-window OLS на изменениях `CLOSE`, `min_ar_pairs=100`, refit each origin; missing adjacent pair не заполняется. B0: последнее известное `CLOSE`.
- `comparison.json` фиксирует `passed=true` на сравнениях A1→A2; `calendar_checks.json` фиксирует `verification_status=provisional_not_independently_verified`.
- Сохранённые A2 и diagnostics manifests отражают `uncommitted_changes` в момент расчёта. **Требуется контрольный rerun из чистого checkout актуального `main`, не переписывая исходные артефакты**. Наличие Git-коммита с исходниками не заменяет повторного вычисления.
- По умолчанию scoring ограничен validation; final test 2026 **не использовать для выбора модели, порогов, признаков и калибровки**. Заключительные ограничения и текущие выводы — [project_status.md](project_status.md).

## 10. Extension contract для моделей и интервалов

Новые модели получают **только историю до текущего `origin_date`**, возвращают прогнозы `h=1…7` и метаданные fit; сохранение прогнозов выполняется до scoring. Новые признаки требуют `published_at/available_at` либо явно зафиксированного консервативного лага; `target_date` определяется календарём. Для supervised `h`-шаговых регрессий обучающая метка созревает только после доступности `C_{t+h}`.

Interval API: `origin_date,target_date,horizon,alpha,lower,upper,calibration_end_date,model_id,pit_status`. Coverage, width и interval score считать на тех же разрешённых target, независимо от RMSE. При добавлении DFM и ML не переиспользовать test для подбора.
