# Backtesting Protocol — USDRUBF

**Версия:** 1.1 · **Дата:** 2026-11-19 · **Владелец:** A  
**Статус:** принято с проверяемым условием доступности данных в 23:51.

## 1. Определение target и origin

- `instrument=USDRUBF`, `timezone=Europe/Moscow` (UTC+3).
- `close_cutoff=23:50:00` — окончание вечерней сессии по текущему расписанию MOEX; для истории использовать календарь и регламент, действовавшие на соответствующую дату.
- `target_price[d]` = цена **последней допустимой сделки строго до 23:50** (не расчетная цена ЦБ и не произвольное поле `CLOSE`). `target_trade_ts` сохранять отдельно.
- `forecast_origin[d]=23:51:00` МСК — предварительный прогнозный срез. Требуется подтвердить, что источник исторических/потоковых данных делает используемые сделки доступными к этому моменту; при задержке сдвинуть origin и задокументировать.
- `h=1,…,7` — следующие **торговые дни USDRUBF** по фактическому расписанию, в том числе возможные выходные торговые сессии.
- Входная цена `F_d` может использоваться только если `available_at(F_d) <= forecast_origin[d]`.

## 2. Фандинг, официальный курс, клиринг

- Использовать только **опубликованный** к origin фандинг и последний **опубликованный** курс ЦБ; для каждого значения хранить `observation_time`, `published_at`, `available_at`, `vintage`, `rule_version`.
- По спецификации USDRUBF от 08.09.2026: расчетная цена для вариационной маржи — последний опубликованный курс ЦБ (п. 2.1.7); `SwapRate` связан с VWAP торгов 10:00–15:30 и курсом ЦБ, установленным в этот торговый день (п. 2.1.3).
- Клиринг mark-to-market следует после 23:50. **Его результаты, еще не опубликованные к 23:51, исключаются**. Даты действия официального курса не смешивать с датами его публикации.
- Исторические изменения параметров фандинга и режимов торгов проверять с `effective_from`, а не применять актуальные правила ретроспективно.

## 3. Выбор цены, пропуски, качество

Основной ряд: последняя биржевая сделка USDRUBF в разрешенной сессии до 23:50, из подтвержденного источника trades / корректно проверенного поля. Преференция granular trades, а не дневной агрегат, который может быть сформирован позднее origin.

**Предварительные правила (до анализа ликвидности):**
- `age = 23:50:00 - target_trade_ts`; `age <= 5 min`: fresh; `5 < age <= 15 min`: accepted + stale_flag; `age > 15 min` или нет сделок: target missing.
- Для `missing` запрещено: переносить старую цену без ограничений, заменять ее расчетной ценой / курсом ЦБ, вставлять искусственные нулевые доходности.
- Альтернативные пороги 5/30 мин, а также VWAP 23:40–23:50 проверяются как sensitivity (не подбирать по final test).
- Отделять отсутствие фактических сделок от неудачной загрузки/неполного потока данных. Отчитываться об исключениях, их датах и возможном смещении.
- Если `F_d` отсутствует, этот origin не используется для основных моделей, основанных на известном `F_d`. Если target в `d+h` отсутствует, прогноз отмечается `unscored`, а не автоматически сдвигается на следующий валидный день: **h остается номером торгового дня**.

## 4. Point-in-time и walk-forward

Для каждого `x` требуется `available_at(x) <= forecast_origin[d]`, включая цену `F_d`, курс ЦБ, фандинг, показатели ликвидности, макроряды, историю ошибок. Известные позже пересмотры не использовать; при отсутствии винтажей явно маркировать `pseudo-PIT`.

- Сначала выбрать train/validation/final test по хронологии после аудита длины истории; test не открывать для model selection.
- На каждом origin модель видит только исторические обучающие пары, у которых **метка уже стала доступна** к этому origin.
- Масштабирование, PCA, отбор признаков, импутацию и гиперпараметры оценивать только на разрешенных окнах.
- Для ML-коррекции использовать историю **реальных OOS-прогнозов** DFM, у которых target уже известен на дату новой коррекции. `h=7` имеет задержку как минимум семь торговых шагов.
- Отдельно фиксировать пересекающиеся прогнозы горизонтов и учитывать зависимость ошибок (HAC/block bootstrap при уместности).

## 5. Benchmarks

B0 RW: `F_hat[d+h|d]=F_d`. B1 drift: `F_d + h*mu_hat_d`. B2 spread/funding-regression: прогноз будущего изменения на лаги `F_d−S_CBR_asof` и/или опубликованного `SwapRate`. Далее PCA, DFM, DFM+ML, интервальная коррекция.

## 6. Метрики и честность сравнения

Точечные: `MAE_h`, `RMSE_h`, `Bias_h`, `RMSE_ratio_h=RMSE_model_h/RMSE_RW_h`; считать **на общих origin/target**; `n_h` и даты сообщать. Интервалы: empirical coverage, mean width, interval score, отдельно по `h` и уровню (первый вариант 90% и 95%).

Нельзя объявлять значимость только на основании `RMSE_ratio<1`. Показывать анализ по режимам и чувствительность к пропущенным дням.

## 7. Обязательные автоматические тесты

1. `target_trade_ts < close_cutoff`; `available_at(F_d) <= forecast_origin`.
2. Нет feature со временем публикации после forecast_origin.
3. Нет обучающих строк с target, еще не известным к обучающему origin.
4. Отсутствующие/устаревшие котировки не превращаются в нулевые движения.
5. Расчетный/официальный курс не используется как рыночный target.
6. `d+h` — именно h-й следующий торговый день, даже при пропуске котировки; нет lookahead при смене регламента.
7. `train/val/test`, fit-transform и доступность ошибок для ML строго разделены.
8. Сопоставление модельных прогнозов строго по `(forecast_origin, target_timestamp, horizon)`.

## 8. Файлы прогнозов

Обязательные колонки: `model_id, model_version, forecast_origin, target_date, target_timestamp, horizon, prediction, train_end_timestamp, data_version`; дополнительно `close_cutoff, target_trade_ts, quote_age_seconds, quote_status, asof_price_source`; для интервалов `alpha, lower, upper, calibration_end_timestamp`.

Для каждого эксперимента сохранять конфигурацию, hash Git-коммита, версию источника, схему PIT и все прогнозы (включая `unscored`).
