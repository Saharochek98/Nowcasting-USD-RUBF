# Объединённый датасет USDRUBF и внешних факторов — v2

**Статус:** предварительный датасет, `conditional EOD / pseudo-PIT`  
**Файл:** `data/processed/model_dataset_usdrubf_all_features_v2.csv`  
**Период:** 26.04.2022–18.11.2026  
**Размер:** 1 160 строк × 30 столбцов  
**Частота:** одна строка на торговую дату USDRUBF  
**Цель:** подготовка факторов для прогноза рыночной цены `close` USDRUBF на следующие 1–7 торговых дней.

> **Важное ограничение.** Датасет ещё не подтверждён как исторически точная point-in-time (PIT) выборка. Время формирования прогноза в команде определено как момент **после доступности полной дневной свечи USDRUBF**, без установленного точного часа. Для отдельных внешних показателей использованы явно описанные предположения о задержке данных. До согласования с исследовательским руководителем этот файл следует применять как **предварительную факторную панель**, а не как окончательно проверенную PIT-выборку.

## 1. Структура и назначение

Основой служит исходная выгрузка дневных свечей MOEX ISS `USDRUBF_daily_2026-11-18.csv`. Все её исходные поля сохранены **без изменения значений**. К ним присоединены:

- официальный курс USD/RUB Банка России;
- два варианта фандинга USDRUBF (`SWAPRATE` текущего и предыдущего торгового дня);
- разность между `close` USDRUBF и выбранным курсом ЦБ;
- ключевая ставка Банка России и RUONIA;
- спотовая цена нефти Brent по данным EIA;
- дневное историческое значение USD/CNH (`Price`) из Investing.com; **тип BID/ASK для исторического `Price` не установлен**;
- служебные даты исходных наблюдений, необходимые для проверки временной доступности.

**Целевая переменная** — `close` из дневных свечей MOEX ISS (`interval=24`), **не** официальный курс ЦБ и **не** `SETTLEPRICE` из итогов торгов. Признаки в строке даты `t` предназначены для прогноза на будущие торговые даты `t+1`…`t+7`, но пользоваться ими можно лишь после выполнения соответствующих условий доступности.

## 4. Правила объединения по датам и доступности

**База (`date`).** Ровно одна строка на дату дневной свечи USDRUBF. Торговые даты, в том числе рабочие субботы, сохранены в исходном порядке. Дневные цены USDRUBF не интерполировались, пропущенные торговые дни искусственно не создавались.

**Курс ЦБ.** Использован последний курс с датой **вступления в силу** `<= date`. Это консервативное правило по дате действия. Если прогноз будет формироваться после объявления следующего курса ЦБ, к этому моменту может быть доступна более свежая информация; это ещё не отражено в v2. Публикация и вступление в силу — разные события.

**Фандинг.** Сохранены два варианта: за текущую торговую дату и за предыдущий торговый день USDRUBF. Текущий фандинг допустим для прогноза лишь после реальной публикации. Точное историческое `available_at` отсутствует в CSV. Участник B (Research Lead) ещё не зафиксировал точное время прогноза; это открытая методологическая задача.

**Ключевая ставка.** Присоединён последний действующий уровень ставки с датой записи `<= date`; между изменениями уровень сохраняется. Дата действия не должна автоматически считаться датой первоначального объявления решения.

**RUONIA.** Для строки `date` выбрано наблюдение с `DT < date` и `DateUpdate.date <= date`. Это исключает механическую подстановку значения за ещё не завершившуюся текущую дату. Вместе с тем `DateUpdate` может быть временем обновления записи, а не первоначальной публикации; **строгое PIT-подтверждение отсутствует**.

**Brent.** Выбрана последняя цена с датой наблюдения `<= date − 10 календарных дней`. Лаг **10 дней — предварительное, намеренно консервативное предположение**, а не проверенный график исторических релизов EIA. В исходном XLS были указаны метаданные последнего выпуска: `Latest Data for: 11/17/2026`, `Release Date: 11/18/2026`, `Next Release Date: 11/25/2026`. Они сами по себе не доказывают, когда публиковалась каждая прежняя строка.

**USD/CNH.** Использован экспорт Investing.com `USD to CNH Historical Exchage Rates.csv`, поле `Price` (дневное историческое значение, не подтверждённое как BID). Для торговой даты USDRUBF `t` выбирается последнее наблюдение Investing.com с датой **строго раньше `t`**. Сдвиг по исходной дате сделан как предварительное ограничение от утечки будущего. При этом Investing.com не приводит в CSV ни точный час закрытия дневной записи, ни исторический `published_at`: из выбранного лага **нельзя заключить**, что значение достоверно доступно при любом точном `forecast_origin`, например в 00:15 МСК следующего календарного дня. До уточнения времени формирования прогноза и регламента обновления источника признак остаётся `pseudo-PIT`. Источник USD/CNH был изменён по сравнению с v1; при дальнейшем моделировании нельзя без переобучения и фиксации версии заменять один источник котировок другим.

**Спред.** Рассчитывается как `close_t − cbr_usdrub_effective_t`. Из-за использования `close_t` спред допустим **только после фактической доступности дневной свечи t**.

### Что запрещено делать при моделировании

- Нельзя использовать признаки за `t+h` для прогноза из `t`.
- Нельзя считать `date`, `begin`, `end`, `cbr_effective_date` или `DateUpdate` доказательством точной минуты фактической публикации.
- Нельзя заменять отсутствующий `SWAPRATE` нулём или подставлять `CLOSE` из иной биржевой выгрузки вместо исходного таргета.
- Нельзя использовать 2026 год (закрытый финальный test команды) для выбора лагов, признаков, моделей и настройки гиперпараметров.

### 5.5. Особенности исходных свечей MOEX

Время `end` в исходном дневном CSV принимает разные значения:

- `23:59:59` — 1 083 строки;
- `23:59:41/42` — 42 строки (2022 год);
- `19:30:21/22` — 35 строк (2024–2025 годы).

Ранее было выявлено **91 несовпадение `close`** и **94 несовпадения `volume`** между дневными свечами MOEX ISS и отдельной выгрузкой **итогов торгов MOEX** на общих датах. Это **разные биржевые источники/агрегации**, поэтому данные не смешивались: для целевой переменной сохранён только `close` из исходных дневных свечей.

Выборочная реконструкция по минутным свечам:

- **30.09.2022:** `close=58,84`, `volume=59 551` из дневной свечи точно воспроизводятся по минутам календарного дня; `CLOSE=58,31`, `VOLUME=60 053` из итогов торгов воспроизводятся при объединении вечера предыдущего дня с основной частью текущего дня до 19:00.
- **19.03.2025:** исходная свеча `close=85,70`, `volume=209 985`, `end=19:30:22`. До 19:30 накоплено 209 837 контрактов, после полной минуты 19:30 — 210 535. Это **согласуется** с обрезанием агрегации внутри минуты, но не доказывает точное время последней сделки или правила формирования свечи. Остаётся необъяснённым расхождение объёма итогов торгов на 700 контрактов при одном из сравнений.

**Оставшееся ограничение:** механизм всех 91 расхождений не подтверждён индивидуально, точные исторические времена готовности свечей и некоторых внешних данных не установлены.

### 7.1. Как получить исходные выгрузки и повторить сборку v2

Скрипт сохраняет **исторический снимок v2**, а не автоматически скачивает обновлённые котировки. Даты выгрузок и исходные файлы важны: данные поставщиков могут корректироваться задним числом, поэтому повторная выгрузка «за тот же период» не обязана совпасть побайтово.

Исходные файлы следует поместить в **одну локальную папку**, путь к которой передаётся через `--sources`. В GitHub их дополнительно загружать не требуется.

Для исходного PDF ключевой ставки необходим `pymupdf`, для исходного EIA `.xls` — `xlrd`. Если используются уже подготовленные CSV-версии этих двух файлов, скрипт работает на стандартной библиотеке Python. Установить дополнительные зависимости можно одной командой:

```powershell
python -m pip install pymupdf xlrd
```

С корня репозитория, подставив собственный путь к папке источников:

```powershell
python scripts/build_external_features.py --sources "D:\USDRUBF_sources" --calendar data/processed/trading_calendar.csv --output rebuilt_usdrubf_v2.csv --compare data/processed/model_dataset_usdrubf_all_features_v2.csv
```

Программа создаст файл `rebuilt_usdrubf_v2.csv` и **сравнит все байты** с версией, сохранённой в GitHub. При отличии выведет первую несовпавшую ячейку. Исходный файл в `data/processed/` не перезаписывается. Ожидаемый результат успешной пересборки:

```text
Created rebuilt_usdrubf_v2.csv with 1160 rows and 30 columns
EXACT REPRODUCTION verified; SHA-256: da5b582e622ce5d3efb6fb619c0b9258dc15fc7d18b6d76860ce5fb021107103
```

**Контрольная процедура** (работает **без внешних выгрузок**, поскольку сравнивает GitHub CSV с исходными свечами и календарём, уже сохранёнными в репозитории):

```powershell
python -m unittest discover -s tests -p "test_external_features.py" -v
```

Тесты проверяют структуру, неизменность исходного `CLOSE` и остальных OHLCV, дубликаты, календарь, заполненность, пропуски, корректность сдвига фандинга и формальные ограничения лагов. Дополнительная проверка **полной пересборки** активируется, когда указан путь к внешним исходным файлам:

```powershell
$env:USDRUBF_SOURCE_DIR = "D:\USDRUBF_sources"
python -m unittest discover -s tests -p "test_external_features.py" -v
```

## 8. Что требуется согласовать перед основным бэктестингом

1. Зафиксировать момент `forecast_origin` и проверить фактическую доступность полной дневной свечи.
